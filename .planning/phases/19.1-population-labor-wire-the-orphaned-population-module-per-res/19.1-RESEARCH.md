## Summary

`src/sim/population.ts` (104 lines) is a complete, self-contained pure module for per-residence population (`Residence`/`Resident`/`isEligible`), migration (`MigrationInput`/`netMigration`), labor (`LaborSector`/`allocateWorkers`/`SectorPriority`), and wage policy (`WagePolicy`/`wageBand`) — but it is ORPHANED: it is imported only by `tests/unit/population.test.ts`. Today the live sim models population EXCLUSIVELY through `HOUSING_LIVE_STATS[level].population` (= level capacity, `housingLive.ts:66`) and `effectivePopulation` (merged combined population, `housingLive.ts:103-109`); there is no resident identity, no class/age/employment, no migration, no vacancy, no homelessness. Labor is greedy placement-order allocation (`runner.ts:2729-2744` — no priorities, no sectors, no pinning). Wage policy is a single `policy.wageRate` 0..1 scalar with no imperial reference and no band report.

The wiring strategy that satisfies every locked constraint (goldens untouched, no SaveData growth, byte-identical replay, additive-only API) is: **keep all new per-residence/migration/labor-sector/wage-band state and outputs OUT of the serialized `SimState`/`BuildingState` shapes, and put them on (a) internal-only fields of `BuildingInstance`/`HouseInstance` (precedent: `combinedPopulation`, `civic`, `production` — all "never serialized, so lns/SimState stay byte-identical"), (b) the non-serialized `DerivedSnapshot` (`getDerived()`, ~`runner.ts:1346-1349`; `getStateJson()` serializes `getState()`, NOT `getDerived()` — `runner.ts:2554-2556`), and (c) the read-only `getInspector`/`residenceInspection` internals seam (`runner.ts:2597-2625`, `sim/advisors.ts:283-310`).** All new mutable state must change only inside `tick()` (`runner.ts:291-401`) or a SaveCommand handler, because save/load replays every command then re-ticks from 0 (`fromSaveData`, `runner.ts:2662-2669`) — deterministic per-tick mutation reproduces byte-identically with zero schema change.

The single biggest landmine is the golden byte-identity contract: `tests/golden/golden.test.ts` snapshots `getStateJson()` after the `foodChainMap` scenario → `JSON.parse(runner.getStateJson())` (`golden.test.ts:27,61`). Any new field inside `BuildingState.house` (the `toBuildingState` shape at `runner.ts:3187-3228`), `SimState` (`runner.ts:1914-1941`), or a change to worker-pool/tax/wage arithmetic breaks it. Verified this session: the golden + economy + labor + advisors + population suites (51 tests) are green today as the baseline. POP-02's migration must therefore be defined against a vacancy (capacity − occupancy) that is 0 under today's always-full invariant, so the golden scenario sees zero migration delta — and occupancy scaling must NOT feed `workerPool`/`tax` unless the planner confirms no golden scenario hits it (see Pitfall 3).

**Primary recommendation:** Wire `population.ts` as a deterministic internal layer over the existing level-based population — internal-only per-house `residents` micro-state (POP-01), month-cadence `netMigration` applied to occupancy with 0 golden delta (POP-02), sector-grouped `allocateWorkers` replacing greedy `tickLabor` plus a new `setLaborSectorState` SaveCommand (POP-03), and a pure `wageBand`/`unemploymentBand` report surfaced via `DerivedSnapshot` + advisors (POP-04). No new external packages; no data-catalog changes (module-local constants per the balance-parity rule, `config.ts:1-12`).

### Pattern 1: Internal-only per-house micro-state (golden-byte contract)
**What:** Add fields to `HouseInstance` (walkers.ts:88-122) that are never copied into `BuildingState.house` (runner.ts:3188-3211), exactly like the existing `combinedPopulation`, `civic`, and `production` internals.
**When to use:** Any new sim behavior that must survive save/load WITHOUT a SaveData schema change — replaying commands then ticking recomputes it byte-identically (`fromSaveData`, runner.ts:2662-2669).
**Example (precedent, verbatim):**
```typescript
// src/sim/walkers.ts:118-122 — the established pattern for non-serialized sim state:
  /** Civic wellness (Phase 12): health/literacy/entertainment 0..100 stats
   *  driven by walker-delivered service access. Internal only — never
   *  serialized, so goldens/SimState stay byte-identical. */
  civic?: HouseCivicState;
```
New POP-01 fields follow the same comment discipline: `residents?: Resident[]` and `nextResidentId?: number` on `HouseInstance`; the `toBuildingState` projection (`runner.ts:3187-3228`) must NOT copy them.

### Pattern 2: DerivedSnapshot as the golden-safe read surface
**What:** `getDerived()` returns the cached `derivedSnapshot()` (`runner.ts:1346-1349`); `getDerived()` is the ONLY place advisors read live numbers (`game/advisors.ts:104`). `getStateJson()` serializes `getState()` — not the derived snapshot — so **new fields on `DerivedSnapshot` (runner.ts:136-163) cannot change goldens**.
**When to use:** Every new aggregated number (demography/resident stats, migration, wage band, unemployment band). Add fields to the interface AND populate them in `derivedSnapshot()` (runner.ts:1242-1344); consumers pick them up through `game/advisors.ts` automatically.
**Example (new fields to add):**
```typescript
// DerivedSnapshot additions (runner.ts:136-163 — additive, golden-safe)
residentCount: number;            // == population (consistency invariant)
residentsByClass?: { plebeian: number; patrician: number };
immigration?: number; emigration?: number; homeless?: number;
wageBand: { band: 'below' | 'at' | 'above'; relative: number };
unemploymentBand: { label: string; rate: number };
```

### Pattern 3: New SaveCommand kind (pin/pause labor sectors)
**What:** `SaveCommand` is an exhaustive union (`types.ts:75-99`); `applyCommand` dispatches every kind and throws on unknown (`runner.ts:3288-3290`). Governance/mission/request/trade commands all follow this pattern (paused path enqueues, live+replay handlers apply).
**When to use:** Any new player action — pin/pause/restore-auto is one. Add `{ kind: 'setLaborSectorState'; sector: string; pinned?: boolean; paused?: boolean }` to the union; add the `applyCommand` branch (the exhaustive `never` guard forces the branch or fails typecheck); the handler stores into a private map (precedent: `marketConfigs`, runner.ts:2561-2563) and works under `replaying=true` during paused-drain.
**Example (dispatch pattern to extend — verbatim):**
```typescript
// src/sim/runner.ts:3262-3263 — precedent command whose handler I verified this session:
  } else if (cmd.kind === 'requestRoyalSubsidy') {
    runner.requestRoyalSubsidy();
```
A labor-sector command would be the same shape: `} else if (cmd.kind === 'setLaborSectorState') { runner.setLaborSectorState(cmd.sector, cmd); }`.

### Anti-Patterns to Avoid
- **Growing `BuildingState.house` or `SimState` with per-residence fields** — instant golden break; the splice of `toBuildingState` (runner.ts:3187-3228) must stay exactly as-is.
- **A live "immigration/emigration walker" spawn this phase** — new walker types would enter `SimState.walkers` (`toWalkerState`, runner.ts:3230-3244) and alter every golden/determinism suite. CONTEXT narrows the scope to "derived deltas" — keep walker spawning out of scope.
- **Reordering `tickLabor` allocation without re-verifying scarcity tests and winnability probes** — the greedy placement-order loop (runner.ts:2729-2744) is asserted indirectly by labor tests (`assigned ≤ required`, `assigned ≤ pool`) and tune-dependent scenarios; reorder then run the full suite + `winnability-probe.test.ts`.
- **Adding BALANCE keys or CONFIG keys** — `config.ts:1-12` re-exports `data/balance.ts`; the balance-parity gate (`DATA-02`) rejects new keys that don't preserve equivalence. New tuning (sector priorities, imperial wage, occupancy rates) stays module-local.

## Common Pitfalls

### Pitfall 1: Golden byte-identity break via serialized-resident fields
**What goes wrong:** `tests/golden/golden.test.ts` (`golden.test.ts:27,61`) deep-equals recorded fixtures to `JSON.parse(runner.getStateJson())`; `getStateJson` = `JSON.stringify(getState())` (runner.ts:2554-2556). Any new key inside `BuildingState.house` (runner.ts:3188-3211) or `SimState` (runner.ts:1925-1940) — even `undefined`-valued optional keys — changes the JSON and fails the suite.
**Why it happens:** The temptation is to serialize the resident model "like normal state."
**How to avoid:** Put residents on `HouseInstance` (internal), populate only `residenceInspection(...)` internals output and `DerivedSnapshot` — never `toBuildingState`. Run `npx vitest run tests/golden` before commit.
**Warning signs:** A diff in `food-chain-golden.json`; a `getStateJson()` string whose only change is `house` keys.

### Pitfall 2: `allocateWorkers` `pinned` semantics are weaker than the requirement
**What goes wrong:** The pure function's `pinned` flag only prevents early loop break — under an empty pool a pinned sector still gets `assign = 0`:
```typescript
// src/sim/population.ts:84-89 (verbatim)
  for (const s of ordered) {
    if (!s.pinned && remaining <= 0) break;
    const assign = Math.min(s.needed, remaining);
    s.assigned = assign;
    remaining -= assign;
  }
```
so "pinned sector keeps its workers under scarcity" is NOT what the code delivers.
**Why it happens:** The module was written and unit-tested in isolation (population.test.ts:31-41 tests only priority ordering), never wired.
**How to avoid:** Implement "pin = guaranteed minimum" in the runner wiring layer: allocate pinned sectors first with their prior `assigned` reserved before the pool is split, or extend `allocateWorkers` to accept a reserve amount. Do not assume the existing `pinned` branch grants an allocation guarantee.
**Warning signs:** A test asserting a pinned sector holds its workers under a shrunken pool fails; `pinned` seemingly does nothing.

### Pitfall 3: Migration/occupancy scaling silently changes the economy
**What goes wrong:** If occupancy below capacity feeds `workerPool` (economy.ts:26 sums `effectiveWorkers(b)`) or tax (`effectiveTaxPerTick`), then any house that starves (famine emigration) or is under-occupied changes treasury/wages → rating numbers diverge from the golden scenario and many integration/determinism suites re-derive different states.
**Why it happens:** The cleanest "real" model scales workers by occupancy; the golden scenario was recorded under always-full houses.
**How to avoid:** In this phase keep behavior deterministic and golden-neutral: `workerPool`/tax/`populationOf` continue to use `effectivePopulation`/`effectiveWorkers`/`effectiveTaxPerTick` (capacity-based) — the occupancy/resident model is a **derived layer** (report + inspector + migration fill) layered over capacity. Migration, by construction, has `capacityAvailable = capacity − occupancy = 0` whenever the city is full, so the golden food-chain city yields zero migration delta. If a later phase wants occupancy to affect production/tax, that is a deliberate balance change requiring golden regeneration — flag it explicitly.
**Warning signs:** `tests/golden` or `tests/determinism/*` failures after wiring migration; migration delta != 0 in the golden scenario.

### Pitfall 4: New internal state must be mutated ONLY under replayable paths
**What goes wrong:** Save/load replays commands then re-ticks (`fromSaveData`, runner.ts:2666-2669). If resident/migration state mutates in a getter or outside `tick()`/command handlers, a loaded runner diverges from the original and the determinism suites (`tests/determinism/*.test.ts`, 16 files) fail.
**Why it happens:** Derived-on-read shortcuts look stateless but read live mutable fields in inconsistent order.
**How to avoid:** All residency/migration mutations happen inside `tick()` on the month cadence (`tickCount % 40`, precedent runner.ts:312/336/356/377) or inside the `setLaborSectorState` handler; getters (`getDerived`, `getInspector`, `getLaborSectors`) only read. Add `tests/determinism/population-determinism.test.ts` asserting `loaded.getStateJson() === original.getStateJson()` after running the new year-cadence paths.
**Warning signs:** A save→load round-trip changes a housing/resident-derived number; a determinism test flakes only when resident features are on.

### Pitfall 5: Advisors panicking on empty cities (total-function rule)
**What goes wrong:** `advisorPanels` composes exactly 13 panels and every value must trace to a real getter (`game/advisors.ts:99-101`); the labor/demography panels read `source.getDerived()` + `getEmployment()`. A wage-band projection that throws on `population === 0` or a missing sector map breaks the advisor tab for empty cities.
**Why it happens:** New aggregate rows that assume resident data exists.
**How to avoid:** Make `wageBand`/`unemploymentBand`/resident stats TOTAL functions over `DerivedSnapshot` (guard `population>0`, `imperialReference||1` — already in `wageBand`, population.ts:101); set `noData` flags where appropriate; mirror the existing care in `sim/advisors.ts:283-310` (append fields only when defined).

## Open Questions

1. **Must migration ever change *city* population totals, or only redistribute within capacity?**
   - What we know: CONTEXT locks "effects are derived deltas, never in getState()" and "goldens unchanged". `netMigration` is bounded by `capacityAvailable` (population.ts:66-67), and today houses are always at capacity (vacancy 0) ⇒ delta 0.
   - What's unclear: Whether the phase is allowed to create vacancy (e.g., famine-emigration under-filling a house) that changes per-house occupancy in observable (non-golden) scenarios, or whether migration is purely a citywide report number for now.
   - Recommendation: Implement the under-occupancy + refill model (it is the only way `netMigration` is ever nonzero and observable), but keep the *city capacity totals* unchanged so `populationOf`/ratings are stable. Confirm via a targeted test.

2. **Pinning semantics:** does "pin" guarantee a minimum allocation under scarcity, or only mark a sector to retain its current assigned workers across ticks?
   - What we know: the pure `allocateWorkers` `pinned` branch does not reserve pool (Pitfall 2).
   - What's unclear: Which behavior the milestone-audit expects.
   - Recommendation: Default to "reserve-guard" (pinned sectors are filled before the general pool split) — the stronger, more user-meaningful reading.

3. **Which housing/evolution signals gate residency churn** (e.g., should losing a requirement mid-month trigger instant resident drop, or only at month cadence)?
   - What we know: requirement-loss already decrements counters and can devolve (housing.ts:159-210); `foodShortageEffects().emigration` is per-house state (housing.ts:399-412).
   - Recommendation: run all residency deltas on `tickCount % 40` (single cadence) to keep replay simple and byte-identical.

4. **Where exactly the wage-band row lands:** labor panel vs demography panel vs both?
   - What we know: labor panel already shows Employed/Unemployed/Jobs/Fill (game/advisors.ts:188-202); finance panel shows the raw Wage Rate (game/advisors.ts:146).
   - Recommendation: put "Wage vs Imperial" + "Unemployment band" in the labor panel (theme-appropriate) and leave finance unchanged (avoids advisor test churn).
