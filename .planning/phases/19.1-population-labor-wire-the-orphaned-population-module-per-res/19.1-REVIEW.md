# Code Review: Phase 19.1 (population-labor)

## Summary

Reviewed the POP-01/02/03/04 wiring: per-residence population (tickResidency + residentsForHouse), month-cadence migration (tickPopulationMigration), sector-priority labor allocation (buildLaborSectors / applySectorAssignments / setLaborSectorState), and the wage/unemployment-band reporting rows. Determinism constraints are respected: no new `Math.random()`/`Date.now()`/`new Date()` in `src/sim` (verified against the diff; the only `Date.now()` in runner.ts is the pre-existing `savedAt` metadata line), `getStateJson()` stays byte-identical (new internals live only on `HouseInstance` and are not copied by `toBuildingState`), and the pinned-reserve semantics are implemented at the runner level as required. Save→load round-trip of `setLaborSectorState` verified empirically (no command duplication, config restored). The 72 phase tests pass.

One critical defect was found and reproduced empirically: the `palatine` building (the only workers>0 catalog type missing from `TYPE_SECTOR`) is permanently de-staffed and deactivated by the new sector pipeline — a regression against the legacy `tickLabor`, which the tests do not cover. Two design-level warnings and four minor issues follow.

### CR-01: `palatine` is not in `TYPE_SECTOR` — permanently de-staffed and deactivated

**Severity:** Critical
**Location:** src/sim/labor.ts:46-88 (TYPE_SECTOR), src/sim/labor.ts:149-172 (applySectorAssignments), src/sim/runner.ts:3000-3004 (activation loop)

**Description:** `TYPE_SECTOR` maps every job-bearing building type to a sector — except `palatine` (Governor Palace, `workers: 40`, `src/sim/buildings.ts:191-194`), the only `workers > 0` catalog type missing from the map. The new `tickLabor` pipeline:

1. `buildLaborSectors` skips it (`sectorOf` → null), so its 40 jobs are missing from every sector's `needed` and from `getLaborSectors()`.
2. `applySectorAssignments` (labor.ts:153-158) zeroes `workersAssigned` for **every** labor-connected building with `workersRequired > 0` — including palatine — but no sector ever re-assigns it.
3. The activation loop (runner.ts:3003) then calls `setActive(b, 0 >= 40)` → **`false` every tick**.

The legacy `tickLabor` (git show 2add081:src/sim/runner.ts:2729) staffed every labor-connected building greedily, so a connected palatine was staffed and active. The regression is real gameplay impact: palatine is placeable once the population threshold is met (`unlockedGov`, governance.ts:29, `CONFIG.govPalatineThreshold`), and labor walkers connect it (`nearestBuildingNeedingLabor`, walkers.ts:896-901). Empirically confirmed with a probe (buildLaborSectors with farm+palatine reports total sector needed = 1; applySectorAssignments leaves palatine at 0).

**Impact:**
- Palatine permanently inactive (can never become active again).
- `totalJobs` (economy.ts:39-43) still counts its 40 jobs, so `assignedWorkers`/`totalJobs` mismatch: the labor panel "Unemployed" is inflated by up to 40 and "Fill" can never reach 100% while a palatine exists.
- `getLaborSectors()` never shows the palace's jobs, so sector `needed` understates true demand.
- Violates the preserved invariant "surplus fills all jobs" (labor.test.ts) whenever a palatine is placed.
- Not caught by any test: labor-sectors.test.ts's `sectorTown` and `fake()` fixtures only use mapped types.

**Suggested fix:** Add the palace to a sector in `TYPE_SECTOR` (e.g. `palatine: 'commerce'` — government buildings forum/senate already map to commerce), and add a regression test that places a labor-connected palatine in a surplus pool and asserts `workersAssigned > 0` / `active === true`:

```ts
// src/sim/labor.ts
const TYPE_SECTOR: Record<string, string> = {
  // ...
  forum: 'commerce',
  senate: 'commerce',
  palatine: 'commerce',
  // ...
};
```

### WR-01: Pinning an unstaffed sector is sticky-zero — it can never regain workers

**Severity:** Warning
**Location:** src/sim/runner.ts:2982-2996 (tickLabor reserve step)

**Description:** A pinned sector's reserve is its **prior** `laborSectorAssigned` value: `const give = Math.min(s.needed, prior, remaining)`. If a sector has `prior === 0` (pinned while the pool was empty, or after the pool shrank to 0 for one tick), the reserve is 0 forever — and because pinned sectors are excluded from the general allocation (`sectors.filter((s) => !s.pinned)`, runner.ts:2993-2996), the sector never receives workers again, even when the pool later grows to a surplus. The player must manually unpin to recover.

This also silently diverges from the pure `allocateWorkers` pinned branch (population.ts:82-92), which would staff a pinned sector up to `min(needed, remaining)` — the phase explicitly says the pure branch is "NOT relied on," but the divergence is user-visible. The "surplus fills all" invariant is violated for any pinned sector with zero prior staffing. The pinned-reserve test only covers pinning a sector that is already staffed (labor-sectors.test.ts:120-143).

**Impact:** A player who pins a sector when it is momentarily unstaffed (or when the pool is empty) permanently loses staffing in that sector with no in-game explanation; sectors show `pinned: true` with 0 assigned indefinitely.

**Suggested fix:** Give a pinned sector a floor of its prior staffing **or** its full `needed` when the pool can cover it — e.g. reserve `Math.min(needed, Math.max(prior, 0), remaining)` won't fix the zero case by itself; instead reserve `prior` but let the general allocation fill remaining demand for pinned sectors too when `remaining > 0` after the priority pass (pinned = guaranteed floor, not an upper cap). At minimum, document the sticky-zero behavior and add a test pinning an unstaffed sector before a surplus pool appears.

### WR-02: `residentCount` and `residentsByClass` disagree after famine emigration

**Severity:** Warning
**Location:** src/sim/runner.ts:1546-1547, 1566-1577

**Description:** `DerivedSnapshot.residentCount` is the capacity-based population (`Σ effectivePopulation`, documented "== population by construction"), while `residentsByClass` sums the live internal `residents` arrays. After a famine-emigration month (tickPopulationMigration splices up to `FAMINE_EMIGRANTS_PER_MONTH` residents per starving house, runner.ts:722-737), the internal total is smaller than capacity until immigration refills it — so in the same snapshot, `plebeian + patrician < residentCount`. A consumer rendering both (population header + class breakdown) shows totals that do not reconcile. The mismatch is transient (refills within a month or two) but visible in the HUD-derived reports.

**Impact:** Inconsistent population reporting in the same DerivedSnapshot; any UI summing the class rows contradicts the population row during/after famine. Currently no game consumer renders `residentsByClass` side-by-side with `residentCount`, so impact is latent — but the contract ("residentCount == population by construction") is misleading.

**Suggested fix:** Either compute `residentCount` from the same internal residents as `residentsByClass` (Σ `h.residents.length`), or document in the interface that `residentCount` is capacity-based while `residentsByClass` is live and may sum to less; consider adding `homeless`/drained accounting so the two reconcile (residentCount = Σ class rows + pending vacancy).

### IN-01: Phantom `TYPE_SECTOR` entries for non-existent catalog types

**Severity:** Info
**Location:** src/sim/labor.ts:49, 51-52, 54-56

**Description:** `vegetable_farm`, `cattle_ranch`, `fishing_wharf`, and `reservoir` do not exist in the `BUILDINGS` catalog (src/sim/buildings.ts:30-251) — only `farm`/`orchard` food types and `well`/`fountain` water types are placeable. These are dead mappings that suggest buildings the game doesn't have, and they contradict the header comment ("Every type with workers (>0) maps to exactly one sector").

**Suggested fix:** Remove the phantom entries or replace them with a comment noting the catalog currently lacks those types.

### IN-02: Misleading comment about `allocateWorkers` going negative

**Severity:** Info
**Location:** src/sim/runner.ts:2980-2981

**Description:** The comment says the pure-function pinned branch of `allocateWorkers` "is NOT relied upon (it would go negative on an empty pool)." It cannot go negative: `assign = Math.min(s.needed, remaining)` with `remaining >= 0` never produces a negative assignment (population.ts:82-92). The runner-level reserve is a legitimate design choice, but the stated rationale is false and will mislead future maintainers.

**Suggested fix:** Reword to state the real reason (the pure branch staffs pinned sectors up to `needed` on a growing pool, while the runner reserve must preserve *prior* staffing; and the runner needs per-sector tracking for the reserve floor anyway).

### IN-03: `wageBand` band comparison inconsistent with ratio at reference 0

**Severity:** Info
**Location:** src/sim/population.ts:100-105

**Description:** `relative` guards division with `p.imperialReference || 1`, but the band comparison uses the raw reference: with `imperialReference === 0`, any `wageRate > 0` reports band `'above'` while `relative` is computed against 1. Unreachable in production (`IMPERIAL_WAGE_REFERENCE = 0.3`), but `wageBand` is an exported pure function with an inconsistent contract at the boundary.

**Suggested fix:** Use the guarded reference in the comparisons too (or document that reference must be > 0).
